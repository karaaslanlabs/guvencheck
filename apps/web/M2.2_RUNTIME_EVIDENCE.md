# M2.2 Runtime Evidence

This evidence has two explicitly separate classes.

## Real local HTTP runtime evidence

`npm run evidence:m2.2` starts the built Karaaslan Agent Platform local task runtime in a separate Node process behind a loopback HTTP server. The GüvenCheck shadow adapter submits each controlled call-site sample with `POST /tasks`, captures the returned task id, polls `GET /tasks/:id` until a terminal state, and verifies HTTP readback from the runtime's default `InMemoryTaskRepository`. Set `AGENT_PLATFORM_API_ENTRY` to the platform's built `apps/api/dist/index.js` before running it.

Persistence/readback in this evidence means successful HTTP readback from that default in-memory repository during the lifetime of the same local Agent Platform Node process. The reported persistence/readback rate does not demonstrate restart durability, disk- or database-backed persistence, or production persistence. Accordingly, the 10/10 result below is only a process-lifetime in-memory HTTP readback result and must not be used as a broader company-level persistence claim. Changing the runtime repository or adding persistence infrastructure is outside M2.2 scope. If the `persistenceReadback` metric name is retained, this narrower meaning should remain explicit until a future backlog item introduces a more precise name or durable repository evidence.

The generated JSON is the source of truth for the 10 sample task ids, terminal statuses, POST-only shadow latencies, full POST-to-terminal-to-GET readback latencies, success rate, and persistence/readback rate. It also exercises a real connection outage and a real HTTP request that deliberately does not respond to verify fail-open timeout behavior.

Verified local run (2026-08-22): 10/10 tasks succeeded and 10/10 were read back from the same process-lifetime `InMemoryTaskRepository` in a terminal `succeeded` state. Returned ids were `m2-2-runtime-1` through `m2-2-runtime-10`; each had a successful `GET /tasks/:id` response before that local runtime process ended. Real loopback HTTP shadow POST latency was min 2 ms, p50 4 ms, p95/max 36 ms. Real end-to-end POST → terminal completion → GET readback latency was min 6.62 ms, p50 13.40 ms, p95/max 40.12 ms. The injected connection outage preserved the exact product-result object. A deliberately non-responding HTTP server with a 25 ms test timeout also preserved the exact result (observed 28.93 ms). These values describe this controlled local run and are not production-network, restart-durability, or durable-persistence claims.

The full end-to-end measurement includes terminal polling and GET readback. It is evidence-run latency, not product response latency. The product awaits only shadow submission. When `AGENT_PLATFORM_SHADOW_URL` is enabled, that awaited POST can add up to the configured 750 ms timeout to the product response. This potential product delay must be evaluated separately from the measured end-to-end evidence latency.

## Unit and controlled harness evidence

`npm test` remains unit evidence for payload mapping, exact product-result identity preservation, outage fail-open behavior, and telemetry isolation. Unit timings and mocked responses must not be reported as real runtime persistence, readback, network latency, or success-rate evidence.

Across both evidence classes, raw image/screenshot bytes and the GüvenCheck risk result are not forwarded. Production risk-decision ownership remains in GüvenCheck. The optional shadow URL is not required by Closed Testing, and disabled or unavailable shadow infrastructure cannot change the product result.
